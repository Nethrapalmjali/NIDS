Network Intrusion Detection System

Detecting attacks hidden in one-way traffic with machine learning.

NIDS captures live network connections, extracts flow-level features, and uses an ensemble of gradient-boosted models to classify traffic across 12 attack categories, including DDoS, port scanning, brute force, botnet and web attacks. When it raises an alert, it also explains in plain language why the traffic was flagged.

01 · Problem statement

Why traditional monitoring falls short

Modern networks generate far more traffic than people can review by hand. Attacks blend into normal traffic, and signature-based tools miss anything they don't already have a rule for.

One-way anomalies

Continuous one-directional flows can mean data exfiltration, scanning or command-and-control beaconing, and they are hard to spot in aggregate traffic.

Noise from legitimate traffic

High volumes of normal traffic bury the few malicious flows that matter.

Look-alike attacks

Low-and-slow attacks (Slowloris, credential stuffing) imitate legitimate request patterns.

Static rules go stale

Rule-only systems cannot recognise variants of attacks they have no signature for.

Alerts without context

Analysts receive raw alerts with no explanation, which slows triage and response.

Our solution

A lightweight, ML-driven monitor that analyses flow direction and behaviour, classifies threats, and raises early, explained alerts on a live dashboard.

02 · Secure architecture

Defense-in-depth by design

The system is split into isolated layers. Each layer has a single job, runs with the minimum privileges it needs, and is guarded by its own control, so a weakness in one layer does not compromise the rest.

Defense-in-depth layers

  • Perimeter: host firewall limits the dashboard to HTTPS from the admin subnet.
  • Detection integrity: model files are hashed (SHA-256) and loaded read-only, so tampered models are rejected.
  • Application: Flask-Login sessions, hashed passwords, CSRF tokens, role checks on every route.
  • Data: SQLite accessed only via parameterised queries; the incident log is append-only.
  • Accountability: every login, acknowledgement and configuration change is written to the audit trail.

Least privilege

  • Capture runs as a dedicated service account with only the raw-socket capability, not full admin rights.
  • The ML engine has no network access; it receives feature vectors and returns labels.
  • Viewer role: read dashboards. Analyst: acknowledge and annotate incidents. Admin: manage users and thresholds.
  • Secrets (Flask secret key, API keys) live in environment variables, never in source code.
  • Captured payloads are not stored. Only flow metadata is kept, which also reduces privacy risk.
03 · Workflow

From packet to explained alert

Each connection passes through seven stages. Detection works on flow metadata, never on packet payloads, which keeps it fast and privacy-preserving.

IP Traffic

Inbound & outbound activity on the monitored interface.

Capture

Python sockets, psutil connection table, traffic simulator.

Feature Extraction

IPs, ports, protocol, bytes, packets, duration.

Traffic Analysis

Flow direction ratio, rates, behavioural windows.

ML Classification

Soft-voting ensemble of LightGBM, XGBoost and CatBoost.

Dashboard & AI

Live charts, threat simulation, incident explanation.

Alert & Log

Severity-ranked alerts stored for investigation.

04 · Security mechanisms & tools

Controls applied, and why

Authentication

Flask-Login session management; passwords hashed with PBKDF2-SHA256 (Werkzeug); login rate-limited to stop brute force against the NIDS itself.

Access control

Role-based access (Viewer / Analyst / Admin) enforced by route decorators, with deny-by-default for any route not explicitly allowed.

Encryption

Dashboard served over HTTPS (TLS 1.2+); session cookies set Secure, HttpOnly, SameSite=Lax.

Input validation

All form and API inputs validated by type and range; IP and port fields parsed with ipaddress; templates auto-escaped against XSS.

Injection safety

Every SQLite query is parameterised; no string-built SQL anywhere in the incident store.

Integrity

Model artefacts verified by SHA-256 before loading, because loading an untrusted Joblib file is code execution.

07 · Evaluation

Measuring the controls and comparing alternatives

Model performance

Each model is evaluated on a held-out, stratified test split with accuracy, macro precision, recall, F1 and false-positive rate. Macro averaging is used so rare attack classes count as much as floods.

ModelAccuracyPrecisionRecallF1FPRInference / flow

LightGBM

Fastest training and inference with a low memory footprint. Best fit for real-time scoring on a 4 GB laptop.

XGBoost

Strong accuracy and regularisation that resists overfitting. Slightly heavier at inference time.

CatBoost

Handles categorical fields (protocol, port class) natively, so needs less preprocessing. Slowest to train.

Performance impact of security measures

Metadata only

Analysing headers and flow statistics instead of payloads cuts CPU and storage cost, and avoids decrypting TLS.

Windowed batching

Flows are scored in short time windows, trading a few seconds of latency for much lower CPU load.

Auth & TLS overhead

Session checks and TLS add milliseconds per dashboard request and do not touch the capture path.

Ethical considerations

Consent & scope. Capture runs only on networks the operator owns or is authorised to monitor. Attack simulations target lab hosts only.

Data minimisation. Payloads are never stored. Flow records are kept only as long as needed, and the explainer sees only aggregated features.

Fairness & transparency. Every alert carries the features that triggered it, so analysts are not asked to trust a black box.

Human in the loop. The system detects and recommends; blocking actions stay a human decision to avoid disrupting legitimate users.

09 · Incident response

Handling an alert end to end

Alert handling follows the NIST SP 800-61 incident-response lifecycle.

1 · Preparation

Roles defined, baseline traffic profiled, models trained, playbooks for each of the 12 classes.

2 · Detection & analysis

Ensemble flags a flow; severity is scored; the AI explainer states what happened, which features triggered it, and the likely technique.

3 · Containment

Analyst acknowledges the alert and applies the recommended action: firewall block on the source IP, rate-limit, or isolate the host.

4 · Eradication & recovery

Remove the root cause (close the port, reset credentials, clean the bot), then monitor for recurrence.

5 · Post-incident

Incident log reviewed; confirmed samples added to training data; thresholds tuned.

Strengths

  • Early warning: one-way flows are flagged before an attack completes.
  • Explained alerts shorten triage time for less-experienced analysts.
  • An append-only incident log with timestamps supports forensics and CERT-In reporting.
  • The built-in simulator lets the response playbooks be rehearsed safely.

Limitations

  • Detection-only (IDS, not IPS): containment needs a human action.
  • Encrypted payloads are not inspected, so some web attacks are inferred only from flow shape.
  • A single sensor is itself a point of failure and can be overwhelmed by a large flood.
  • Model quality depends on how representative the training data is.
10 · Innovation

What makes this different

Direction-aware detection

Treats one-way traffic as a first-class signal, which catches exfiltration and scanning that volume-based tools overlook.

Ensemble ML

Three gradient-boosted models vote, which reduces the blind spots any single model has.

Explainable alerts

Every incident comes with a plain-language narrative and recommended next step.

Built-in attack lab

DDoS and brute-force simulation to test detection and train analysts without a real attack.

Roadmap

Active response: optional automatic firewall rules for high-confidence alerts (IPS mode).

Distributed sensors: several capture agents feeding one central analyser.

SIEM export: forward alerts as Syslog/CEF to Wazuh or Splunk; SHAP values for per-feature explanations.
