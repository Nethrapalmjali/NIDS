Network Intrusion Detection System

Detecting attacks hidden in one-way traffic with machine learning.

NIDS captures live network connections, extracts flow-level features, and uses an ensemble of gradient-boosted models to classify traffic across 12 attack categories, including DDoS, port scanning, brute force, botnet and web attacks. When it raises an alert, it also explains in plain language why the traffic was flagged.

01 · Problem statement

Why traditional monitoring falls short

Modern networks generate far more traffic than people can review by hand. Attacks blend into normal traffic, and signature-based tools miss anything they don't already have a rule for.

One-way anomalies

Continuous one-directional flows can mean data exfiltration, scanning or command-and-control beaconing, and they are hard to spot in aggregate traffic.

Noise from legitimate traffic

High volumes of normal traffic bury the few malicious flows that matter.

Look-alike attacks

Low-and-slow attacks (Slowloris, credential stuffing) imitate legitimate request patterns.

Static rules go stale

Rule-only systems cannot recognise variants of attacks they have no signature for.

Alerts without context

Analysts receive raw alerts with no explanation, which slows triage and response.

Our solution

A lightweight, ML-driven monitor that analyses flow direction and behaviour, classifies threats, and raises early, explained alerts on a live dashboard.

02 · Secure architecture

Defense-in-depth by design

The system is split into isolated layers. Each layer has a single job, runs with the minimum privileges it needs, and is guarded by its own control, so a weakness in one layer does not compromise the rest.

Defense-in-depth layers

  • Perimeter: host firewall limits the dashboard to HTTPS from the admin subnet.
  • Detection integrity: model files are hashed (SHA-256) and loaded read-only, so tampered models are rejected.
  • Application: Flask-Login sessions, hashed passwords, CSRF tokens, role checks on every route.
  • Data: SQLite accessed only via parameterised queries; the incident log is append-only.
  • Accountability: every login, acknowledgement and configuration change is written to the audit trail.

Least privilege

  • Capture runs as a dedicated service account with only the raw-socket capability, not full admin rights.
  • The ML engine has no network access; it receives feature vectors and returns labels.
  • Viewer role: read dashboards. Analyst: acknowledge and annotate incidents. Admin: manage users and thresholds.
  • Secrets (Flask secret key, API keys) live in environment variables, never in source code.
  • Captured payloads are not stored. Only flow metadata is kept, which also reduces privacy risk.
03 · Workflow

From packet to explained alert

Each connection passes through seven stages. Detection works on flow metadata, never on packet payloads, which keeps it fast and privacy-preserving.

IP Traffic

Inbound & outbound activity on the monitored interface.

Capture

Scapy packet capture (raw sockets via Npcap), psutil interface counters, or held-out replay with attack simulation.

Feature Extraction

IPs, ports, protocol, bytes, packets, duration.

Traffic Analysis

Flow direction ratio, rates, behavioural windows.

ML Classification

Soft-voting ensemble of LightGBM, XGBoost and CatBoost.

Dashboard & AI

Live charts, threat simulation, incident explanation.

Alert & Log

Severity-ranked alerts stored for investigation.

04 · Security mechanisms & tools

Controls applied, and why

Authentication

Flask-Login session management; passwords hashed with salted scrypt (Werkzeug); 5 failed logins per IP trigger a 5-minute lockout, so the NIDS itself can't be brute-forced.

Access control

Role-based access (Viewer / Analyst / Admin) enforced by route decorators, with deny-by-default for any route not explicitly allowed.

Encryption

Dashboard binds to localhost by default; for remote access it sits behind a TLS reverse proxy, with NIDS_HTTPS=1 marking cookies Secure. Cookies are always HttpOnly and SameSite=Lax; a strict Content-Security-Policy and anti-framing headers are set on every response.

Input validation

All form and API inputs validated by type, length and allow-list; CSRF token required on every POST; Jinja templates and the dashboard's JavaScript escape all output against XSS.

Injection safety

Every SQLite query is parameterised. Database triggers make the audit trail append-only and block deletion of incidents.

Integrity

Model artefacts verified by SHA-256 before loading, because loading an untrusted Joblib file is code execution.

Run the real system

Real-time dashboard

The repository contains the full working system: the training pipeline, the detection engine and the Flask dashboard. The engine classifies flows every second, writes incidents to SQLite with an explanation built from per-feature SHAP contributions, and charts the host's live network throughput.

Quick start

# Docker (recommended)
docker compose run --rm -e NIDS_ADMIN_PASSWORD=... nids init
docker compose up -d            # http://127.0.0.1:5000

# or Python 3.10-3.12
pip install -r requirements.txt
python -m nids.app init         # create admin account
python -m nids.app check        # verify models + versions
python -m nids.app serve        # production server (Waitress)

Traffic sources

  • --source replay: streams held-out CIC-IDS2017 flows the models never saw, as a continuous live feed. Analysts can inject any of the 12 attack classes, and the dashboard shows live agreement with ground truth.
  • --source live: real packet capture with Scapy. Packets are assembled into bidirectional flows (closed on FIN/RST, 15 s idle or 60 s active timeout) and scored as they close. On Windows this needs Npcap; on Linux, root or CAP_NET_RAW.

Production-ready operations

Hardened deployment

Waitress WSGI server; Docker image runs as non-root with a read-only filesystem, all capabilities dropped and a built-in health check; all configuration via environment variables; dependencies pinned to the exact versions the models were trained with.

Observability

/healthz and /readyz probes, a Prometheus /metrics endpoint (flows, per-class counts, incidents, dropped flows, queue depth, engine heartbeat) and rotating log files.

SIEM & SOAR integration

Each incident is appended to a JSON-lines feed for Filebeat, Wazuh or Splunk, and can be pushed to a webhook (Slack, Teams, SOAR) asynchronously so detection never stalls.

Analyst workflow

Filter incidents by status, severity and class; acknowledge with notes; export to CSV with formula-injection protection; change passwords; admins manage roles and disable accounts.

Resilience

Capture never blocks: when the engine falls behind, flows are dropped and counted. The flow table and caches are memory-bounded against scan floods, and a failing batch is logged without stopping detection.

Continuous integration

Every push runs lint, 23 unit and integration tests, and a Docker build with a container readiness smoke test, then republishes this website automatically.

Training data

The CIC-IDS2017 dataset

CIC-IDS2017 was published by the Canadian Institute for Cybersecurity (University of New Brunswick). It was recorded over five working days, 3–7 July 2017, on a testbed network: a victim network of Windows, Ubuntu and macOS hosts and servers, attacked from a separate attacker network. Background traffic came from profiled user behaviour (web, email, FTP, SSH). The captured packets were converted into bidirectional flows with CICFlowMeter, and each flow is described by 78 statistical features and a label.

Capture timeline

Tue 4 JulFTP-Patator, SSH-Patator: credential brute force

Fri 7 JulBotnet (Ares), port scans, DDoS (LOIC)

Class distribution (labelled flows, before de-duplication)

The data is heavily imbalanced: benign flows outnumber SQL-injection flows by roughly 100,000 to 1. That is why this project uses class-weighted training and macro-averaged metrics.

From raw dataset to training set

  1. Load all 8 daily CSV files (MachineLearningCSV), keeping the 28 selected features and the label.
  2. Map labels to 13 classes. Infiltration (36 flows) and Heartbleed (11) are dropped as too rare to learn.
  3. Clean: coerce to numeric and drop rows with NaN or ±∞ (present in the Flow Bytes/s column).
  4. De-duplicate: 378,461 identical rows removed, so no flow appears in both training and test sets.
  5. Balance: keep up to 250k benign and up to 50k flows per attack class.
  6. Split: stratified 80% train / 20% test, fixed seed 42 for reproducibility.
  7. Weight: square-root inverse class frequency, so rare classes matter without dominating.

The 28 features (all computable live from packet headers)

Only features that a lightweight sensor can compute from packet headers in real time are used, so the same model scores both the dataset and live captured traffic. Payloads are never inspected.

What the results show

  • Volumetric and scanning attacks are solved problems at flow level. DDoS, Hulk, GoldenEye, port scan and SSH/FTP brute force all reach an F1 of about 99.5% or higher.
  • Timing features matter. The longest packet gap (Flow IAT Max) and flow duration rank near the top, because slow-rate DoS and botnet beaconing are defined by when packets arrive, not by how many.
  • TCP initial window sizes are strong fingerprints of the attack tools used in the dataset. That boosts test accuracy but may transfer less well to other networks, which is a key reason to retrain on local traffic.
  • The web attacks are the real weakness. XSS and web brute force target the same server and port with similar request sizes. Most of their errors are confusion with each other, not missed attacks.

LightGBM

Fastest to train (68 s), and its SHAP contributions power the alert explanations. However, its 63-leaf trees make it the slowest at inference (~79 µs/flow) and the weakest on rare web attacks.

XGBoost

Best single model: highest accuracy, highest macro precision, lowest false-positive rate among single models, with ~15 µs/flow inference and 88 s training.

CatBoost

Symmetric (oblivious) trees give the fastest inference (~1.3 µs/flow) and the highest single-model recall and detection rate, but it takes the longest to train (449 s) and has twice the false-positive rate.

Why an ensemble?

Soft voting averages the three models' probabilities. It achieves the best macro F1 and recall of all four options while keeping XGBoost's low false-positive rate. The cost is the combined inference time of all three models (~95 µs/flow), which still allows over 10,000 flows per second on a single CPU core, far more than a small office network produces.

Performance impact of security measures

Metadata only

Analysing headers and flow statistics instead of payloads cuts CPU and storage cost, and avoids decrypting TLS.

Windowed batching

Flows are scored in short time windows, trading a few seconds of latency for much lower CPU load.

Auth & TLS overhead

Session checks and TLS add milliseconds per dashboard request and do not touch the capture path.

Ethical considerations

Consent & scope. Capture runs only on networks the operator owns or is authorised to monitor. Attack simulations target lab hosts only.

Data minimisation. Payloads are never stored. Flow records are kept only as long as needed, and the explainer sees only aggregated features.

Fairness & transparency. Every alert carries the features that triggered it, so analysts are not asked to trust a black box.

Human in the loop. The system detects and recommends; blocking actions stay a human decision to avoid disrupting legitimate users.

09 · Incident response

Handling an alert end to end

Alert handling follows the NIST SP 800-61 incident-response lifecycle.

1 · Preparation

Roles defined, baseline traffic profiled, models trained, playbooks for each of the 12 classes.

2 · Detection & analysis

Ensemble flags a flow; severity is scored; the AI explainer states what happened, which features triggered it, and the likely technique.

3 · Containment

Analyst acknowledges the alert and applies the recommended action: firewall block on the source IP, rate-limit, or isolate the host.

4 · Eradication & recovery

Remove the root cause (close the port, reset credentials, clean the bot), then monitor for recurrence.

5 · Post-incident

Incident log reviewed; confirmed samples added to training data; thresholds tuned.

Strengths

  • Early warning: one-way flows are flagged before an attack completes.
  • Explained alerts shorten triage time for less-experienced analysts.
  • An append-only incident log with timestamps supports forensics and CERT-In reporting.
  • The built-in simulator lets the response playbooks be rehearsed safely.

Limitations

  • Detection-only (IDS, not IPS): containment needs a human action.
  • Encrypted payloads are not inspected, so some web attacks are inferred only from flow shape.
  • A single sensor is itself a point of failure and can be overwhelmed by a large flood.
  • Model quality depends on how representative the training data is. The live flow builder approximates CICFlowMeter, so scores on real traffic from a different network will be lower than the test-set numbers until the model is retrained on local data.
10 · Innovation

What makes this different

Direction-aware detection

Treats one-way traffic as a first-class signal, which catches exfiltration and scanning that volume-based tools overlook.

Ensemble ML

Three gradient-boosted models vote, which reduces the blind spots any single model has.

Explainable alerts

Every incident comes with a plain-language narrative and recommended next step.

Built-in attack lab

DDoS and brute-force simulation to test detection and train analysts without a real attack.

Roadmap

Active response: optional automatic firewall rules for high-confidence alerts (IPS mode).

Distributed sensors: several capture agents feeding one central analyser.

SIEM export: forward alerts as Syslog/CEF to Wazuh or Splunk; SHAP values for per-feature explanations.
